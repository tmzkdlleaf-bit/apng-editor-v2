# R3 — 내보내기 안정성·속도 (검토 보완 3)

`tests/r0-repro.spec.js`의 `[R3-*]` 테스트를 통과시키고, 용량 맞추기·굽기 속도를 줄이는 묶음이다. R1·R2는 끝났다고 가정한다.
CLAUDE.md 규칙을 따른다. 결과 파일(바이트)은 지금과 같아야 한다 — 속도만 바뀌고 결과는 바뀌면 안 된다.

## 시작 전에

1. `npx playwright test tests/r0-repro.spec.js -g "R3-"` 로 실패 확인.
2. 개선 전 기준 숫자를 잰다(보고에 표로): 768×768 · 24프레임 데모 문서로
   (a) APNG 내보내기 총 시간, (b) 코코포리아 APNG 용량 맞추기 총 시간과 후보 수, (c) 굽기만 걸린 시간.
3. 읽을 파일: `src/core/export/bake.js`, `src/export/encode.js`, `encode-worker.js`, `fit.js`, `index.js`, `src/ui/export/index.js`, `tests/s5-1.spec.js`, `tests/s5-2.spec.js`

## 항목

### R3-1. 메모리 경고만 있을 때 크래시

- 원인: `fit.js`의 `pass()`가 메모리 경고로 모든 크기를 건너뛰면 `best`가 `null`인 채 `best.buf`를 읽는다.
- 고칠 방향: 결과가 하나도 없으면 `code: 'memory'`와 `warning`을 담은 오류를 던진다(`exportAnimation`과 같은 모양).
  내보내기 창은 이 오류를 "캔버스·프레임 수가 커서 메모리가 부족합니다. 크기를 줄여 보세요." 같은 한국어 안내로 보여준다.
  목표 용량이 없는 용도도 메모리 경고가 나면 다음 크기(x0.75…)로 내려가 볼지는 보고에서 선택지로 제시만 한다(구현하지 않음).

### R3-2. 인코더가 끝나지 않는 경우

- 원인: `encode.js`의 `postEncode()`가 워커 `onmessage` 안에서 예외를 던지면 Promise가 영원히 대기한다.
- 고칠 방향: `postEncode`를 try/catch로 감싸 `fail(err)`. 입력 검사(`frames` 배열·크기)는 워커를 만들기 전에 한다.
- `exportAnimation`의 `allowLargeMemory: true`가 실제로 굽기를 하도록 `bakeFrames`에 한도 해제(`maxMemoryMB: Infinity` 등)를 넘긴다.

### R3-3. 인코더 워커 재사용 (속도)

- 지금: `encode()` 호출마다 새 워커 + WebP wasm 로딩. 용량 맞추기는 최대 24번.
- 고칠 방향: 워커 하나를 재사용하는 인코더를 만든다(예: `createEncoder()` → `{ encode, dispose }`).
  `fitToTarget`/`exportMany`는 시작할 때 하나 만들어 끝(성공·실패·취소 모두)에 `dispose`한다. 취소하면 워커를 종료하고 다음 요청 때 새로 만든다.
  기존 `encode()` 함수는 같은 동작으로 남겨 두어 다른 호출부와 테스트가 깨지지 않게 한다.
- 워커에 프레임을 보낼 때마다 전체 복사(`slice`)하는 것은 유지해도 되지만(같은 굽기 결과를 여러 번 인코딩하므로),
  복사가 필요 없는 마지막 사용처에서는 생략할 수 있는지 판단해 보고한다.

### R3-4. 굽기 대기 시간 (속도)

- 지금: 프레임마다 `await setTimeout(0)` — 브라우저가 최소 4ms로 늘려서 120프레임이면 약 0.5초 대기.
  `getImageData` 결과를 `new Uint8ClampedArray(id.data)`로 한 번 더 복사한다.
- 고칠 방향: 마지막 양보 후 일정 시간(기본 16ms)이 지났을 때만 양보한다. 진행 표시·취소 반응성(취소 1초 안에 멈춤 — 기존 테스트)은 유지.
  `id.data`를 그대로 쓴다(새로 만든 배열이라 복사 불필요).

### R3-5. 비트맵 정리 (메모리)

- `ui/assets.js`의 `invalidate()`가 `ImageBitmap`·anim 프레임을 `close()`하지 않는다. 지울 때 닫는다.
  (R1에서 내보내기 창 쪽은 이미 고쳤다. 같은 방식인지 확인.)

### R3-6. 성능 테스트 안정화

- `s5-1`/`s5-2`는 효과마다 25ms 한 가지 기준인데, 색수차는 평소 22ms라 부하가 조금만 있어도 실패한다.
- 고칠 방향(기본값 제안): 효과마다 기준을 따로 둔다(평소 값의 2배 정도, 최소 25ms). 또는 측정 횟수를 늘려 중앙값으로.
  어느 쪽을 골랐는지와 효과별 기준표를 보고에 적는다. 측정이 너무 느린 효과(색수차·하프톤)는 따로 표시만 하고 이번 묶음에서 효과 코드는 고치지 않는다.
